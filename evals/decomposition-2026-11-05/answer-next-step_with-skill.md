```
git diff --name-only HEAD | grep -Ei '(test|spec)'
```

Непустой вывод значит: ты изменил тест, а не код. Зелёный прогон тогда ничего не говорит о баге — он говорит, что проверка ослаблена, удалена или тест пропущен. Это разные вещи, и в выводе они выглядят одинаково.

Порядок дальше, по убыванию риска:

1. **Проверь, что тронуто.** Команда выше. Непустой список — открой каждый файл, сравни проверяемое поведение с версией до правки (`git diff HEAD -- <файл>`). Если assertion стал слабее — верни его, чини код. 2–5 минут.

2. **Прогони весь набор, не только упавший файл.** Правка в общем коде могла сломать другой тест, который ты не запускал.
   ```
   pytest -q        # или твой раннер: npm test, go test ./..., cargo test
   ```
   5–20 минут в зависимости от размера набора.

3. **Проверь, что diff не шире причины.** Открой `git diff HEAD` целиком. Каждая изменённая строка должна быть объяснима той ошибкой, которую ты чинил. Строка «заодно поправил» — отдельный коммит, не этот. 3–5 минут.

4. **Ищи тот же дефект в соседних местах.** Если причина была «не проверяется отсутствие пользователя», grep по сигнатуре:
   ```
   grep -rn '\.profile\|getUser(' --include='*.py' .
   ```
   10–15 минут.

5. **Коммит с причиной в сообщении.** `fix: return 404 when user id is absent` — не `fix tests`. Сообщение должно называть поле, которое было пустым, и что ожидалось. 1 минута.

Проверить, что работа сделана: шаг 2 зелёный на полном наборе, шаг 1 даёт пустой вывод, шаг 3 — diff только по коду.

Следующее действие: запусти команду из первой строки и посмотри, пустой ли вывод.
