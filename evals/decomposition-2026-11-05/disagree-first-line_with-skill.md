Нет. Храни деньги в целых копейках (`int`/`BIGINT`) или в `Decimal`/`NUMERIC`, не в `float`.

1. **Сложение не сходится.** `0.1 + 0.2` в double равно `0.30000000000000004`. В деньгах: 10 копеек + 20 копеек дают число, которого нет в десятичной записи. Проверка, которая падает:
```python
assert 0.1 + 0.2 == 0.3   # AssertionError
```

2. **Ошибка накапливается.** Тысяча прибавлений по `0.01` даёт не `10.00`. Ошибка растёт с числом операций, поэтому итог зависит от порядка сложения — один и тот же набор платежей даёт два разных баланса.

3. **Сравнение врёт.** `if balance == 0:` не сработает, когда баланс «ноль» после вычитаний. `if a == b` для двух путей расчёта одной суммы даёт ложное «не равно».

4. **Округление не определено.** `round(2.675, 2)` даёт `2.67`, потому что `2.675` в double чуть меньше `2.675`. Правило округления (half-up или half-even) в float не выражается — только в `Decimal` с явным `quantize`.

5. **Точный диапазон кончается.** Double хранит целые точно до `2**53 = 9007199254740992`. В копейках это ≈ 90 трлн ₽. Выше прибавление 1 копейки не меняет число: `x + 1 == x`.

Как хранить по слоям:
- Python: `int` в копейках для хранения; `decimal.Decimal` для процентов, курсов, налогов, с явным `quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`.
- SQL: `BIGINT` (копейки) или `NUMERIC(19,4)`. Никогда `FLOAT`, `REAL`, `DOUBLE PRECISION`.
- JSON/API: целое `12345` или строка `"123.45"`. JSON-число `123.45` парсится в double в JS и большинстве парсеров.
- JS: `BigInt` для копеек или строка; `Number` безопасен только до `2**53`.

Цена: `Decimal` медленнее double и требует указать правило округления в одном месте кода. Это платить обязательно, потому что расхождение в деньгах не откатывается.

Проверка, что сделал правильно: `assert isinstance(balance, int)` и `assert sum(payments) == balance`, где `payments` — список целых копеек.
